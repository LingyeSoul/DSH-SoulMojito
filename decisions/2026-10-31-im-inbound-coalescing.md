# IM 入站合流：同一 peer 的短窗连发合并成一条，先按平台时间重排

日期：2026-10-31。状态：已实施。前篇：`2026-10-31-im-native-session-binding.md`。

## 背景

手机端的 IM 使用习惯是连发短句：「在吗」「睡了吗」「帮我看一眼这个」。在
`2026-10-31-im-native-session-binding.md` 的「入站即插入」下，每条都变成会话里
一条独立的用户消息，宿主 AgentLoop 会为每一条排轮/插话：模型要么在一轮里对着
五条几乎同时出现的消息作答，要么连开五轮把回答拆碎。QQ/OneBot 的平台补发、
`timestamp` 乱序与设备时钟差还会让消息顺序在会话里翻车。

插件此前刻意不做队列（同决策第 3 条「不排队、不去抖」），是因为「排队 + 等人
说完」会违背立即投递。本次反转该取舍：窗口的目的是**收拢一次对话**，不是延迟
投递——窗口只有 600ms，且有硬上限，触限立即冲刷；`runtime.dispose()` 也会冲刷
最后一窗。

## 决定

1. **每个 peer 一条 600ms 短窗**（`IM_COALESCE_WINDOW_MS`，`packages/plugin/src/im/coalesce.ts`）。
   `router.inbound()` 只把消息追加进该 peer 的缓冲并挂一个窗口定时器；窗口到期
   整批冲刷。同一 peer 的纯文本连发合并成**一条** `im-<uuid>` 消息插入绑定会话，
   头部 `（连续 N 条消息）`，尾部仍是 `im_send` 提示。
2. **同 peer 先重排**：冲刷前按 `platformAt ?? receivedAt` 升序排序，同值按本地到达
   序号稳定排序（`orderInboundEntries`）。`platformAt` 只在协议提供时存在：
   QQ 的 `timestamp` 字符串（秒或毫秒）与 OneBot 11 的 `time`（秒）都归一到毫秒；
   微信没有平台时间，保持 undefined。归一化口径统一为「数值 `n > 0 && n < 1e11`
   视为秒并乘 1000，否则按已是毫秒原样用」。
3. **只合并纯文本**：批次里任何一条带媒体（`media.length > 0`）就不合并，按排序
   逐条投递——附件摘要与本地路径必须与各自的消息正文待在一起。单条批次同样走
   原单条路径，正文与日志逐字节不变。
4. **上限是硬的**：缓冲达到 `IM_COALESCE_MAX_MESSAGES`（8）条或正文合计超过
   `IM_COALESCE_MAX_CHARS`（4000）字符，立即冲刷该 peer、撤销窗口定时器，不等窗口。
5. **校验推迟到冲刷**：去重、访问控制、绑定查询、媒体物化都在冲刷里按序执行。
   未绑定对端仍记 `imPendingPeers` 并回一次提示（10 分钟抑制窗口不变）；被拒绝与
   重复的条目只写日志。媒体物化仍排在访问控制与绑定之后（白名单外/未绑定不触发下载）。
6. **窗口是注入接缝**：`ImRouterDeps.scheduleFlush` / `coalesceWindowMs` 供测试注入
   手动调度器，不真等 600ms；`ImRouter.flushPending()` 强制冲刷并等待插入完成，
   供测试与 `runtime.dispose()` 使用。冲刷循环最多 50 轮或 2 秒（持续入站时
   「冲到没有待处理项」永不满足，会无限拖延 dispose），超限只 warn 并返回，
   剩余缓冲交给各自的窗口定时器；dispose 的冲刷失败也不挡 teardown。

## 代价与边界

- **崩溃窗口丢消息**：去重在冲刷时才记。若进程在 600ms 窗口内崩溃，这条消息既没
  插入、去重表里也没有它的键——消息丢失，而不是被当成重放吞掉；平台重连补发时
  会被正常接收。正常卸载（dispose 冲刷）不丢。
- **最多 600ms 延迟**：连发场景下这是「攒成一条」的代价；单发同样在窗口后投递。
- **顺序只在同 peer 内保证**：不同 peer 各自一条窗口，跨 peer 顺序不承诺。
- **回复锚点取批内最后一条**：`replyAnchors` 以排序后最后一条投递的消息为准
  （QQ 被动回复的 `msg_id` 只挂最新的触发消息）；批次中间条目的 `replyTo`
  不再单独保留。
- **`platformAt` 的纠偏能力有限**：缺失时退回 `receivedAt`；平台补发晚到、两个时间
  不一致的乱序只有带平台时间的那一条能完全排对。
- **合流正文可能超过字符上限**：上限约束的是缓冲等待期（合计超过即冲刷），单条
  超长消息仍按原文投递，合并时不做截断。

## 否决项

- **无界队列 / 攒到「用户安静」再投**：延迟不可控，会话可能永远等不到；窗口必须有界。
- **合并含媒体的批次**：附件摘要与正文会错位，媒体投递必须逐条与来源消息绑定。
- **跨 peer 合并**：不同对端的消息不能塞进同一条转发消息（回复目标与上下文都会错）。
- **在 `inbound` 时就去重**：崩溃窗口会留下「已去重」的键但消息没投，平台重放被
  永久吞掉——比丢一条更糟。
- **持久化缓冲**：窗口只有 600ms，落盘的成本与复杂度换不来它要守的那一小段时间。

## 验证

- `packages/plugin/tests/im-router.spec.ts`：窗口内两条合并为一条（头部「连续 N 条」+
  尾部 im_send 提示 + 复数摘要）、`platformAt` 乱序重排、不同 peer 各自成条、含媒体
  批次逐条投递且物化仍在访问控制之后、去重/白名单/未绑定在同批次内各自过滤、
  触到条数上限立即冲刷、群聊合并保留每条 `[昵称]` 前缀、去重只在冲刷时发生
  （`seenDedupe` 计数守卫）、持续入站触到冲刷轮数上限时只 warn 不挂死。
- `packages/plugin/tests/im-runtime-accounts.spec.ts`：窗口里压着消息时 dispose
  先冲刷投递（插入时通道仍在册）再停通道。
- `packages/plugin/tests/qq-channel.spec.ts`：`timestamp` 秒 → 毫秒、已毫秒原样、缺失省略。
- `packages/plugin/tests/onebot-codec.spec.ts`：事件 `time` 秒 → 毫秒、已毫秒原样、缺失省略。
- `packages/plugin/tests/onebot-server.spec.ts`、`packages/plugin/tests/im-runtime-accounts.spec.ts`：
  通道与运行时装配不回归。
