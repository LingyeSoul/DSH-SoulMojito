# IM 扫码：二维码渲染与账号 id 派生（提案 0024 缺陷修复）

> 日期：2026-10-30。状态：已修复。来源：主人实机扫码反馈两处阻塞。

## 问题一：面板不显示二维码

**现象**：点「扫码绑定」后没有二维码，只有一个链接。

**根因**：平台给的是**扫码器要编码的内容**（微信 `qrcode_img_content`、QQ 的
`onQrDisplayed(url)`），不是图片地址。面板把它塞进 `<img src>`，浏览器当成无效
URL，于是破图；`onError` 后退化成链接。服务端从头到尾没有产出过图片。

**方案**：服务端自己渲染。

- 新增 `src/im/qr.ts`：最小 QR 编码器（byte 模式、版本 1–10、四档纠错、8 种掩码
  与罚分）。仓库不能引入第三方依赖，宿主与运行时目录也没有可用实现。
- `ImBindStatus.qrSvg` 携带 `data:image/svg+xml;base64,...`；QQ 与微信的绑定状态机
  在 `waiting` 相位生成它。内容超长编码失败时返回 `undefined`，面板退回链接——
  不因为一张展示图让整次绑定失败。
- 面板原本就有 `qrSvg || url` 的优先级，服务端补上字段后即生效。

**正确性证据**：`tests/qr.spec.ts` 用独立读回器把数据码字从矩阵里取回来逐字节比对
（版本 1–10 全覆盖），并对每个 RS 块做校验子全零检查（标准级约束），外加定位图形、
暗模块与容量表（四档纠错 × 版本 1–10）对照。编码器写错任何一步，这三类断言都会红。

**否决项**：

- **引入二维码库**：破坏零依赖分发；`qrcode-terminal` 之类还会把终端字符画带进
  服务端日志。
- **前端生成**：客户端同样没有实现，且要再维护一份；服务端出图还能被 GET 状态轮询
  直接复用。
- **只显示链接**：微信扫码必须真的有码可扫。

## 问题二：微信账号 id 含 `@` 导致保存失败

**现象**：`saving the WeChat credential failed: weixin context token store got an
illegal accountId "...": only [A-Za-z0-9._-] is allowed`。

**根因**：`ilink_bot_id` 可能是邮箱形状（含 `@`），而账号 id 直接用作密钥/游标/
context-token 的文件名，`ImStore` 只允许 `[A-Za-z0-9._-]`。扫码链路跑到最后一步才炸。

**方案**：新增 `src/im/account-id.ts` 的 `imAccountIdOf(channel, raw)`：

- 合法（且不是 `.`/`..`）→ 原样使用，可读、路径稳定；
- 不合法 → `${channel}-<sha256(raw) 前 12 位>`；
- 原始 `ilink_bot_id` 保留在密钥袋里（重连与去重都要它），展示用 label。

**为什么不放宽 `ImStore` 的允许集**：账号 id 会进文件路径、peerKey 与 HTTP 查询
串；放宽校验等于把路径穿越与编码问题引进来。派生一次，后面全部安全。

## 未覆盖

- 真机扫码仍未验证（无手机）：本轮只保证「有图、图的内容是平台给的字符串」。
  若微信返回的 `qrcode_img_content` 其实是图片 URL 而非内容串，面板会优先用
  `qrSvg`（把那串当内容编码），此时需要改为直接透传——上线前扫一次即可确认。
- QR 只支持版本 ≤10（约 271 字节）。扫码 URL 远小于这个上限；真超了会退回链接。
